# ScLERP planner comparison

The benchmark runs **1,000 trials per condition** by default, for 5,000 trials total:

| Condition | Planner | Environment |
| --- | --- | --- |
| `direct_empty` | One continuous ScLERP + RMRC motion, no random nodes | `empty.xml` |
| `sampled_empty` | ScLERP + RMRC with RRT node sampling | `empty.xml` |
| `sampled_obstacles_1` | Same sampled planner | One cylinder |
| `sampled_obstacles_2` | Same sampled planner | One box |
| `sampled_obstacles_3` | Same sampled planner | Two cylinders |

The three obstacle layouts live in `environments/obstacles_1.xml` through
`obstacles_3.xml`. Their placements are fixed. The existing interactive
`scene.xml` and its randomized cylinders remain available in the viewer.

## Run

From the project directory:

```bash
cmake -S . -B build -DCMAKE_BUILD_TYPE=Release
cmake --build build -j2
ctest --test-dir build --output-on-failure
./build/benchmark --output benchmark-results
```

For a machine without GLFW, configure with `-DBUILD_VIEWER=OFF`. The benchmark
and tests use `planner_core` and never open a viewer. The existing interactive
application is still `./build/testing`.

A quick run or a single condition:

```bash
./build/benchmark --trials 10 --output benchmark-smoke
./build/benchmark --condition sampled_empty --trials 1000 --seed 1 --output empty-results
```

Options are `--trials`, `--seed`, `--condition`, `--output`,
`--max-expansions` (default 1000), and `--validation-checks` (default 240).
`--help` lists the condition names. Output directories may already exist, but
the program refuses to overwrite existing benchmark CSV files.

## Results and interpretation

- `trials.csv`: one row per requested trial, including failures, seed, sampled
  goal pose, planning time, tree size, pose errors, and rejection counts.
- `summary.csv`: trials, success count, success percentage, validated-path
  count and percentage, and mean planning time for each condition.
- `settings.csv`: the seed range, model paths, planner settings, and thresholds.

`success` means the planner reached the goal within **1 mm and 0.001 rad** and
accepted its collision checks. `valid_path_success` additionally requires dense
playback collision checks, limited-joint bounds, and independent MuJoCo endpoint
kinematics to pass. A reached pose can have a joint-limit-violating path: the
existing RMRC solver does not enforce joint limits. Both rates are reported so
that a reached goal is not mistaken for a fully validated motion.

Success rate is `100 * successes / requested_trials`. Failed goal sampling,
failed edges, and exhausted expansion budgets stay in that denominator. Setup
errors, such as a missing model file or an unwritable output directory, stop the
runner with a nonzero exit code. A completed benchmark returns zero even when
some planners fail. Trial rows are flushed after each trial; summary rows are
flushed after each completed condition.

Planning time covers planning and its collision checks, excluding model loading,
goal sampling, final dense validation, and CSV output. It is not a hardware
execution time. Collision checks retain the project's existing semantics: floor
planes and directly connected robot links are excluded. Dense sampled checks
are not continuous swept-volume collision detection.

## Reproducible workload

Each trial starts from the model's `home` keyframe. Goals are generated by drawing
joint configurations within model limits, computing FK, and rejecting workspace,
self-collision, and obstacle violations. Position and orientation therefore have
a common valid joint solution. No failed planner task is replaced with an easier
goal. Sampling stops after the configured attempt limit and records a failure
if no acceptable goal is found.

Trial `i` uses seed `first_seed + i - 1`. Goal, workspace, quaternion, cylinder,
and biased-expansion random streams are separate and reset for every trial.
The two empty-space planners receive identical goals for matching trial seeds.
Obstacle conditions apply scene-specific rejection, so the same seed need not
produce the same goal across different environments. Repeated runs reproduce
tasks and paths on the same build/platform; timings can vary.

Empty-space sampled planning should be close to 100% for reachable goals, but
this is an expectation to measure. A reachable endpoint does not guarantee that
one continuous screw path avoids self-collision or that RMRC converges along
it. Node sampling can provide an alternate route. Failure counts and pose errors
help distinguish these cases instead of discarding them.

## Modules

`MotionPlanner` in `include/planner.hpp` owns reusable robot and collision models.
`sampleGoal()`, `plan(goal, mode)`, and `validatePath()` are shared by the headless
runner and interactive application. Kinematics, ScLERP, and RMRC are in
`source/planner.cpp`; node sampling and tree operations remain in `sampler.cpp`
and `rrt_star.cpp`. The condition table and CSV reporting are in
`source/benchmark.cpp`.

Direct mode interpolates a single home-to-goal screw. Its integration density
scales with translation (one base interval per `maximum_step`) and rotation
(one per 0.2 rad), using `sclerp_steps_per_edge` integration steps per interval
and the same RMRC settling budget as a sampled edge. These integration samples
are trajectory configurations, not randomly sampled planner nodes. Direct
playback preserves those configurations. Sampled mode retains the existing
short-edge RRT behavior and joint-interpolated playback.

Dense validation checks every playback interval at
`ceil(validation_checks / animation_frames_per_edge)` subdivisions (at least
one). With defaults, that is ten checks per playback interval: 240 per sampled
RRT edge, or ten between successive direct-mode RMRC configurations.
